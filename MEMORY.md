## Patterns

- **Embedded-attachment dual-syntax resolver shape (`ADR-016`, `REQ-SB-86-US-02-T01`):** given a plain `list[str]` of vault-relative `.md` paths (no runtime dependency on however the selection was built), read each note's real body via `app/obsidian/frontmatter.py::read_note`, scan it with two separate regexes (a wikilink-embed `!\[\[([^\]|#]+)(?:[#|][^\]]*)?\]\]` and a markdown-image-link `!\[[^\]]*\]\(([^)\s]+)\)`), and resolve each captured target in a fixed fallback order: (1) relative to the referencing note's own containing folder — the real, dominant convention this vault's own notes actually use; (2) every ancestor folder from the note's own folder up to the vault root, recursively searched for the target's own bare filename under an `attachments/`/`files/` subfolder (the real `write_attachments()`/`write_file_companion()` convention) — searching by filename rather than replicating the exact note-slug/message-slug nesting keeps this resolver decoupled from that convention's own internal shape; (3) as a plain vault-root-relative path. A target resolving nowhere is silently skipped, never fabricated, never a hard failure. **Always call `.resolve()` on both the matched path and the vault root before computing the final vault-relative string** — a match reached via a `../` relative traversal from the note's own folder (e.g. a markdown-image-link target) produces a non-normalized path that otherwise fails to dedup against the SAME physical file reached directly by a sibling note; found live via a real two-note dedup check, not by inspection. A target that itself resolves to a real `.md` file is excluded (Obsidian's `![[Note]]` embed syntax is transclusion, not an attachment — including it would silently expand an export beyond the operator's own selection). First concrete instance: `vault_attachment_resolver.py::resolve_embedded_attachments`. Apply the same shape to any future "detect a real on-disk reference inside a note's own body" resolver.

- **Genuinely-unfiltered filesystem-tree read shape (`REQ-SB-86-US-01-T01`):** a real, uncached recursive walk built directly on `Path.iterdir()`/`Path.relative_to()` over `settings.vault_path` (never `vault_writer.list_all_note_paths()`/the in-memory note index, which deliberately excludes OKF-reserved files and `_`-prefixed folders) — sort folders-before-files by computing `child.is_dir()` ONCE per entry and reusing that single boolean for both the sort key and the type decision (see the Constraint below for why calling `is_file()`/`is_dir()` independently is unsafe). First concrete instance: `VaultManager.get_export_tree()` / `GET /vault/export-data/tree`. Verified live: a 4081-entry independent `Path.rglob("*")` cross-check against the real vault matched the endpoint's own flattened output byte-for-byte (0 missing, 0 extra).

- **Message-note readable filenames need time-of-day, not just date, or they collapse right back into indistinguishable names.** `<date> <sender>` alone (the first fix for "messages in a thread all have the same title") still fails whenever the SAME sender posts more than once in a thread on the same day — the common back-and-forth case — since the hash-suffix collision fallback produces a second filename that still just *reads* as "Name" in Obsidian's file view. `<date> <HH:MM> <sender>` fixes it directly and is more informative than a hash. Found live 2026-08-21 during the first real vault-rebuild pull; fixed in both `vault_lib.py` (Hermes-native Skill) and `app/data_access/vault_writer.py`'s `raw_message_note_path`.

- **Raw-HTTP direct-to-LLM client shape (`ADR-011`):** a new `app/data_access/<provider>_client.py` — raw I/O only (build request, send via `httpx`, parse response), a dedicated `<Provider>ClientError(Exception)` raised on every real failure path (network error, timeout, non-2xx, or a response body that doesn't parse into the expected shape — wrap parsing in `try/except`, never let a `KeyError`/`IndexError`/JSON-decode failure escape unhandled), consumes `app.config.settings` directly at call time rather than through the entity's own CRUD Manager (a Manager owns config-at-rest, not runtime dispatch). Mirrors `app/hermes/rest.py`'s existing `httpx`-direct pattern one layer over; first concrete instance is `compass_client.py` (`REQ-SB-82-US-06-T02`). Apply the same shape to any future direct-to-LLM-provider client.

- **Client-side-only "reply to this message" context anchoring, when no backend persistence exists for a chat surface (`ADR-012` point 5):** assign a purely in-memory, never-persisted `localId` to each message at append time (a simple incrementing counter is enough — no `crypto.randomUUID()` needed); on send, resolve the selected `localId` against the CURRENT in-memory message array (a stale/unresolvable reference just falls through to a plain, unanchored send — never a crash or a blocked Send) and prepend the referenced message's own text as a quoted prefix (`"> {parentText}\n\n{newText}"`) to the text actually sent to the backend — never to the rendered bubble, which always shows only the user's own typed text. Clear the selection on every existing thread-reset path (new-chat/agent-switch), not just after a successful send. Built for `AgentChatPanel.tsx` (`REQ-SB-82-US-06-T08`); reusable for any other single-recipient chat surface that wants a reply-to hint without a real message-id/persistence layer.

- **LLM-composing routing/decision function shape (`ADR-012` point 2):** a business-layer function that reasons over real, given data (a roster/history/message, never a hardcoded scenario) should (1) compose the relevant `data_access/<provider>_client.py` module (never `httpx` directly, never a business-layer import from another business module), (2) build the prompt in a dedicated private helper that takes the real given inputs as plain parameters (never reaches into a store/global itself — keeps the function pure/testable via monkeypatch), (3) parse the model's raw reply with a STRICT match against only the real, given candidate set (e.g. a word-boundary-scoped regex over exactly the ids handed in) — returning `None` on zero or 2+ matches, never fabricating/coercing to the nearest string, and (4) deliberately does NOT catch the client's own dedicated error type — the degrade decision belongs to the caller, one layer up, not the routing function itself (mirrors `_reply_via_agent`'s own established try/except-degrade shape, applied one level higher, at the routing decision rather than the reply-generation step). First concrete instance: `moderator.py::route_question_llm` (`REQ-SB-82-US-06-T03`). Apply the same shape to any future LLM-composing routing/decision function.

- **A frontend API client function that needs the raw `Response` (e.g. `.blob()` for a real file download) bypasses the shared `api/client.ts::apiFetch` helper entirely — that helper always resolves via `response.json()`, so it cannot serve a binary/file response.** The bypassing function issues its own `fetch()` call, re-reads `VITE_API_BASE_URL` locally (duplicated, since `client.ts`'s own `BASE_URL` constant isn't exported) and re-implements the same non-2xx → `ApiError(status, await response.text())` mapping `apiFetch` uses, so callers still get one consistent error shape regardless of which path served the response. First concrete instance: `artifactsApiClient.ts::commitExport` (`REQ-SB-85-US-02-T05`), which returns the real downloaded `.sbf` bytes. Apply the same shape to any future endpoint whose real response is a file, not JSON.

- **Narrowly-scoped import-only write path for an otherwise read-only Manager (`ADR-015`):** `data_access/<entity>.py` gains a raw `write_<entity>_json(id, data)` (zero validation, zero defaults, creates its own target directory if missing, always overwrites); the Manager gains a matching `import_<entity>(id, data) -> Entity` that (1) validates `data` by round-tripping it through the Manager's own EXISTING read-side parser (e.g. `_to_pipeline`/`_to_template`) first — a malformed shape raises there and nothing is ever written to disk — then (2) calls the new data_access writer, then (3) returns `self.get_by_id(id)` (read-your-own-write). The Manager's own module docstring is updated in the same change so a stale "read-only for now" claim never sits next to a real writer. First concrete instance: `PipelineManager.import_pipeline` (`REQ-SB-85-US-03-T04`); same-shape sibling `TemplateManager.import_template` (`REQ-SB-85-US-03-T03`). Apply the same shape to any future Manager that needs a narrowly-scoped write path added for one specific caller (e.g. import provisioning) without becoming a general authoring UI.
