- **[2026-08-24] This app's own spacing scale (`tokens.css`) is `--space-1/2/3/4/6/8` — there is no `--space-5`, and CSS silently swallows the mistake rather than erroring.** An undefined custom property makes `var(--space-5)` invalid, which per the CSS spec invalidates the WHOLE declaration it's used in (falling back to that property's own initial value, e.g. `padding-left: 0`) or, worse, the WHOLE shorthand if used inside one (`padding: var(--space-4) var(--space-5)` loses its `--space-4` half too) — no console warning, no visual crash, just quietly wrong spacing that reads as "forgot to style this" rather than "this is broken." Found live (2026-08-24, operator: "Bullet Points appear before the title") in freshly-written vault-note-detail CSS, then found two MORE pre-existing instances via a repo-wide grep for the same pattern (`agents-map.css`'s search input/empty-state, unrelated to that task, broken since whenever they were written). General lesson: after writing ANY `var(--space-N)`, sanity-check N is actually 1/2/3/4/6/8 — and when a spacing rule visibly "isn't applying" despite being present and matched (confirmed via `document.styleSheets` inspection, ruling out a cascade/specificity conflict), check whether the custom property it references actually resolves to something (`getComputedStyle(el).getPropertyValue('--space-N')`) before assuming the problem is elsewhere.

- **[2026-08-24] A plain outer-scope variable mutated INSIDE a component's own render (even indirectly, via a closure returned to a child render-prop like `react-markdown`'s `components`) breaks under React 18 StrictMode's double-invoked renders — the mutation happens twice per actual render, desyncing anything that assumed "once per element."** Found live building the Vault note detail page's jump-to-section ids: a `let headingCursor = 0` incremented each time a custom `h2`/`h3` component rendered, indexing into a pre-computed `headings` array — worked in THEORY (cursor is redeclared fresh each NoteBody render) but broke immediately in practice because StrictMode invokes the SAME heading's render function twice, consuming two array entries for one actual heading and permanently offsetting every id after the first. Fixed by switching to `rehype-slug` (a `github-slugger`-based AST transform that runs ONCE per parse, before React rendering even starts — a pure function of the markdown tree, not a React-render-time side effect) instead of hand-rolling counter-based id assignment. General lesson: any "assign each Nth rendered element some Nth precomputed value" pattern is a React purity violation waiting to surface — do the assignment in a pure pre-render pass (a memo, an AST transform, matching by stable content/key) instead of a counter mutated during render, even one that looks locally correct.

## Patterns

- **Message-note readable filenames need time-of-day, not just date, or they collapse right back into indistinguishable names.** `<date> <sender>` alone (the first fix for "messages in a thread all have the same title") still fails whenever the SAME sender posts more than once in a thread on the same day — the common back-and-forth case — since the hash-suffix collision fallback produces a second filename that still just *reads* as "Name" in Obsidian's file view. `<date> <HH:MM> <sender>` fixes it directly and is more informative than a hash. Found live 2026-08-21 during the first real vault-rebuild pull; fixed in both `vault_lib.py` (Hermes-native Skill) and `app/data_access/vault_writer.py`'s `raw_message_note_path`.

## Constraints

- **Hermes' real local API (`hermes serve`) runs on `127.0.0.1:9119` and authenticates via a
  page-embedded session token, NOT port 8642 with a bearer API key.** Found live, 2026-08-20:
  the original `hermes_client.py` was built from research/documentation that didn't match the
  actually-installed Hermes version (`hermes-agent==0.20.4`) at all — `hermes gateway` is the
  messaging/cron daemon only (confirmed via its own startup banner: "Messaging platforms + cron
  scheduler"), never a REST API. The real backend is `hermes serve`, and its real auth is
  `GET /`'s own HTML embedding `window.__HERMES_SESSION_TOKEN__ = "..."` — a per-install access
  token (`auth_required: false`, not a login credential), sent back as `x-hermes-session-token`
  on every subsequent call. Confirmed by inspecting a live browser dashboard session's own
  network requests (monkey-patched `window.fetch`) and independently replaying the captured
  header via a plain `curl` outside the browser — both succeeded against real endpoints
  (`/api/status`, `/api/sessions`, `/api/sessions/stats`, `/api/config`, `/api/profiles/active`)
  returning real data. Before trusting ANY documented Hermes API shape again, verify it live
  against a real running instance first — the official docs/README did not match reality here.

- **Hermes' `tools/lazy_deps.py` auto-installs pip packages ONLY for its own closed, curated
  `LAZY_DEPS` allowlist (Hermes' own built-in features — e.g. `tool.doc_extract` →
  `firecrawl-anydoc`) — it does NOT generalize to arbitrary packages a custom Skill script
  might need.** A Hermes-native Skill that needs a real third-party dependency (e.g. `pywin32`)
  must instead have its own `SKILL.md` instruct the agent to run
  `terminal(command="pip install <package>")` as an explicit `## Prerequisites` step — real,
  standard, unrestricted (confirmed against Hermes' own bundled skill-authoring guide), and the
  correct mechanism for this, never `lazy_deps.py`. Neither mechanism makes a project's own
  PRIVATE application code (not a pip package) importable from a Hermes-hosted script — that
  still requires duplicating the code into the Skill's own files or `sys.path`-wiring into the
  project's repo (the latter also pulls in that project's full dependency chain for no benefit).
  See `ADR-002`.

- **A Hermes gateway/CLI session's system prompt (`SOUL.md`/`AGENTS.md`) is injected once at session creation, never re-read mid-conversation — and `session_reset.mode` defaults to `none`, so a WhatsApp thread can run indefinitely on a stale prompt.** Editing `SOUL.md` has zero effect on an already-open chat; the operator (or the agent, via the gateway) must send `/new` (or `/reset`) in that specific thread to start a session that actually picks up the change. Found live 2026-08-22: a 2-day-old WhatsApp session kept asking hallucinated, non-schema questions ("Expected Close Date", "which System") for `track-opportunities` a full session after the real SOUL.md/Skill fix had already been deployed.

- **`hermes -p <profile> chat -q "..."` (one-shot cross-profile relay) has no live back-channel — if the target profile's agent tries to ask a clarifying question via its `clarify` tool, the call just blocks and times out (~120s: "agent will decide") rather than actually reaching a human.** Any multi-turn Q&A needed for a delegated task must happen on the calling agent's own live channel (e.g. Primary's WhatsApp turn) first; only the single, fully-consolidated result (marking unanswered fields explicitly, e.g. `(not given)`) gets relayed in one call. Confirmed live 2026-08-22 building `opp-manager`.
