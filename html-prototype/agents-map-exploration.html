Agents Map — layout exploration (BUG-002)

Option D (semantic zoom / drill-down) is the operator's accepted direction (2026-08-11) — Options A/B/C below are kept only as comparison history, not being iterated further. Two concrete refinements against Option D are what's pending final browser sign-off now: (1) rebalancing the drill-down Hub's size against the agent nodes around it, and (2) a new overview entrance animation. See Option D's own section below for both, and the REVIEW-QUEUE.md entry for this pass for the current status.

A — Dynamic angular budget

What it solves well: directly fixes BUG-002's root cause — SECTION_ARC_SPAN_DEG becomes (360 / sectionCount) * 0.8 instead of a fixed 80°, so a Section's own agents can never exceed its own true wedge regardless of how many Sections exist. At today's real scale this renders with the same overall structure as the already-approved reference — no visual regression, just computed instead of capable of silently overflowing. Smallest diff of the four options: one function, one existing (unused) CSS primitive re-activated.

What it costs: once a Section's agent count exceeds the compact threshold (3, tunable), that Section's agents lose their always-visible label — a real readability trade a reviewer should weigh, not hidden in this write-up. A single very crowded Section still visually reads as "busy" even once contained (many small dots close together).

Label/text handling: nodes stay full-size and labeled up to 3 agents/Section; beyond that, the whole Section's nodes switch to .agent-node--compact (already defined in styles.css, never instantiated until now) — unlabeled dots, label floats below on hover/focus. Section titles zigzag near/far by index (see the top-of-file note) so adjacent titles don't crowd as N grows.

Degrades at high count: gracefully — angular containment is guaranteed by construction for any N and any per-Section count; the only degradation is the compact-mode visual density itself (small dots close together read as "a busy Section" rather than colliding text) and, at extreme counts within one Section, dots eventually visually touch even at compact size (not modeled at this dataset's max of 4/Section — worth a documented density ceiling if a future Section ever needs more than ~8-10 agents at this canvas size).

Technical (4 agents) is the only Section over the compact threshold — its nodes render as unlabeled dots; hover/focus any of them to reveal its label. Every other Section (≤3 agents) stays fully labeled, exactly as today.

B — Multi-ring wedge expansion

What it solves well: the strongest containment guarantee of the four — every Section's agents stay within a narrow, fixed angular sliver (capped well inside even a 7-way split), so cross-Section spillover is structurally impossible regardless of density; a crowded Section absorbs agents by stacking same-Type nodes outward in RADIUS instead. This is the closest match to the operator's literal "use the Rings, or even expand outside, but never overlap another Section" framing.

What it costs: the shared outer boundary must grow to fit whatever Section is most crowded with same-Type agents — and this isn't hypothetical: today's real data already has 3 Worker-type agents in Productivity (Email/Meeting/ To-Do Capture), so even the "Today's scale" state below already shows the boundary pulled outward, not only the stress case. A single shared circular boundary also means every OTHER Section's ring/boundary reads slightly smaller/more compressed than it needs to be, just because one Section is crowded — a true per-Section independent boundary (a non-circular, "spiky" outline, each Section's own arc sized to its own max radius) was considered and rejected here only for implementation cost in a static prototype, not on the merits; worth a second pass if this direction is chosen.

Label/text handling: nodes always render full-size and labeled (this option never needs the compact fallback — radial stacking, not angular crowding, absorbs density) — but stacked same-Type nodes sit directly along the same ray at increasing radius, which visually reads as a short radial "stack" rather than a spread; the stacking step (12 units) is sized to always exceed a node's own diameter so labels never overlap vertically along that stack. Section titles use the same near/far zigzag as every other option.

Degrades at high count: the safest of the four for pure containment — angular footprint per Section never grows no matter how many agents pile in; the visible cost is entirely in the shared boundary's radius, which grows roughly linearly with the single most same-Type-crowded Section's own count, not with total agent count across the whole map.

Even at today's real scale, Productivity's 3 same-Type (Worker) agents already stack radially and pull the shared boundary outward — see "What it costs" above.

C — Communication-affinity clustering

What it solves well: directly answers the operator's first ask — "cluster agents together who are communicating with each other" — by grounding placement in REQ-SB-20's own real data shape (per-agent free-text Keywords, already authored in agents-map.html's side panel). Within a Section, agents are ordered so higher keyword-overlap pairs sit angularly closer together (reuses Option A's exact wedge-safe containment math underneath, so it inherits the same never-spills-out-of-wedge guarantee). A new dashed "affinity line" connects agents in DIFFERENT Sections that share a keyword, routed Hub -> Hub (never a direct cross-Section line, matching REQ-SB-20's own "always via both Hubs" rule) — hover any agent to see who it would route to and through which two Hubs. Try it: hover Email Capture (Productivity) or Renewal Tracker (Customers) in the stress state below.

What it costs: REQ-SB-20 isn't built yet — the "relevance" this option visualizes is a simple exact-keyword- overlap count computed client-side in this prototype, a stand-in for whatever real routing-relevance the eventual Hub intelligence actually computes, not a preview of its real output. The within-Section ordering is a greedy nearest-neighbor chain, not a real force-directed layout (out of scope for a static HTML/CSS/JS prototype) — it approximates "closer affinity reads closer," it doesn't compute an optimal arrangement.

Label/text handling: node labels behave exactly as Option A (full label up to 3 agents/Section, compact beyond). The genuinely new text-density risk this option adds is the affinity lines themselves, since every keyword-sharing PAIR draws one — at high agent counts this could become link- spaghetti fast, so lines are dim (15% opacity) by default and only bolded on hover/focus of an endpoint agent, keeping the resting-state view exactly as clean as Option A's.

Degrades at high count: the hover-gating is the degradation strategy — the number of POSSIBLE affinity lines grows roughly with the square of agent count, but only ever a few are visible at once (whatever's connected to the currently-hovered agent), so the resting view never gets busier as agent count grows, only the hover interaction has more to show.

No cross-Section keyword overlap exists in today's real 5-agent data — hover any agent to confirm no affinity line appears. The stress state below has two deliberate cross-Section pairs to demonstrate the mechanism.

Two real cross-Section affinity pairs in this dataset: Email Capture (Productivity) ↔ Renewal Tracker (Customers), sharing the keyword "customer correspondence"; Deploy Watcher (Technical) ↔ Content Planner (Marketing), sharing "changelog." Hover either endpoint of a pair to reveal its Hub-routed line.

D — Semantic zoom / drill-down

What it solves well: the operator's own suggested direction, worked out concretely. At the overview level every agent is ALWAYS a small, unlabeled compact dot — not just past a density threshold like Option A — so crowding is structurally impossible to read as text collision at ANY agent count; this composes Option A's exact wedge-safe containment math with "compact, always" rather than being a fifth independent geometry. Hover/focus any dot to reveal its label. Click a Section's Hub (try it below) and the overview zooms out and swaps to that Section's own dedicated "Agents Tree" view — its agents spread across the FULL 360° instead of a thin wedge, always fully labeled, with room to also show real agent-to-agent relationship lines without competing with any other Section for space. A "Back to Agents Map" button returns to the overview.

What it costs: two real interaction states to build and maintain instead of one (an overview and a per-Section detail view), and the overview alone never shows agent identity without a hover/click — a reviewer who wants to scan "which agents exist" at a glance has to either hover every dot or drill in, unlike A/B/C where up to 3 agents/Section stay labeled by default. The click-to-zoom transition here is a simplified uniform center-zoom (CSS transform+opacity, ~350ms); a production version would zoom from the specific Hub that was clicked, not the canvas center — a small polish item, not a structural gap.

Label/text handling: overview labels are NEVER visible by default (by design — this is the option's whole point), only on hover/focus, reusing the identical already-defined CSS the other options only use conditionally. The drill-down view has room to show every agent's full label plus its type, unconditionally, since it owns the whole canvas — direct (not Hub-routed) affinity lines connect same-Section agents sharing a keyword, always visible (far fewer candidate pairs once scoped to one Section, so no hover-gating is needed here the way Option C needs it for cross-Section pairs).

Degrades at high count: the best of the four at extreme overview density, since nothing is ever labeled by default at that level regardless of N or per-Section count — the real degradation risk moves entirely into the drill-down view instead, once a single Section itself has a very large agent count (not modeled at this dataset's max of 4/Section); that view would eventually need its own density handling (e.g. a secondary compact ring), not built here.

Every dot is unlabeled by default — hover/focus one to reveal its label, or click any Hub to zoom into that Section's own Agents Tree. Refinement 1 (Hub sizing): click the Technical Hub (only 1 agent here) — the Hub node is now visibly smaller than the agent node it groups, not the oversized centerpiece it was before this pass.

Technical (4 agents) is exactly as legible as Sales (1 agent) at the overview level here — both are anonymous dots until hovered or drilled into. Click the Technical Hub to see its 4 agents laid out with room to spare. Refinement 1 (Hub sizing): at this denser scale, the Hub still reads clearly as the connecting element (dashed accent border, center position, converging lines to all 4 agents) without visually outweighing them — confirmed at both scales, not just the sparse 1-agent case.

Refinement 2 — overview entrance animation

Operator's own framing: "They can be all next to each other then a quick scroll then they turn around and became a Circle with KB in the Center." On landing on the overview (and on demand via "Replay intro" below), agents do NOT appear already in their final circular positions:

  1. Flat — every agent renders first as one flat, evenly-spaced row (same unlabeled dot Option D always uses at the overview level); the Knowledge Base, every Hub, and the rings/spokes/boundary/Section titles all start invisible.
  2. Hold — a short pause (~0.9s) with nothing moving, so the flat row is clearly readable as "agents next to each other" before anything happens.
  3. Transition — every agent glides (CSS transition on its own position, ~0.9s) from its flat slot to its real circular position, while the Knowledge Base grows and fades in at the center it vacated, and the Hubs and rings/spokes/boundary/Section titles fade in alongside it.
  4. Settled — an ordinary, fully interactive Option-D overview (hover a dot for its label; this particular demo doesn't also wire click-to-zoom — see the drill-down demo above for that).

Plain CSS transitions/keyframes only (no animation library) — the Knowledge Base's grow-in (@keyframes kbGrowIn) runs alongside the existing looping kbPulse without conflict since they animate different properties; the Hubs reuse the existing nodeFadeIn keyframe already on every node, just fired on a delay.
