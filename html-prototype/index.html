REQ-SB-31 — System Health View (new top-level nav page) — pending browser sign-off

A new system-health.html nav page (operator-directed placement, 2026-08-12) showing: a Health Issues list (an agent whose Provider has no real client is shown Disabled and listed here, per the operator's scoped override — Scenario 3), the MCP/agent-orchestration path's reachability, each configured Provider's availability rolled up per-Provider, and the last capture run's recorded completion time (or its honest absence, if none has ever completed). Two state-switcher groups demonstrate all 8 Gherkin scenarios: "Everything healthy" vs. "Health issues present" (Scenarios 1-4), and "A run has completed" vs. "No run has ever completed" (Scenarios 5-6). Scenario 7 (fresh, not cached, on every reopen) is a text note next to a Refresh affordance, not a unique visual state. Scenario 8 (the run_agent_conversation crash-gap fix) is backend-only and has no UI shape on this page. Composed entirely from existing tokens/components — no new CSS.

REQ-SB-11 — Agent Activity & Error Observability (new top-level nav page) — pending browser sign-off

A new agent-activity.html nav page (placement resolved 2026-08-13, mirroring System Health's own precedent) showing a chronological, cross-agent activity log — every completed background capture run (email, meeting, and once built, to-do), newest first, with its outcome (success, or failure with an honest error detail, never silently dropped) — plus a current status indicator for the Outlook communication channel (reported honestly as direct COM reachability, not "Hermes-wrapped", since no live Hermes connection exists in this codebase yet). Two independent state-switcher groups demonstrate every Gherkin scenario: "Activity recorded" (a mix of successes across both configured capture agents plus one real failure with detail) vs. "No runs yet" (the honest empty state), and "Outlook reachable" vs. "Outlook unreachable". Deliberately does not duplicate any of System Health's own three checks (MCP mount, Provider availability, last-capture-run timestamp) — see the page's own header note. Composed entirely from existing tokens/components (reuses styles.css's own .log-list/.log-item chronological-log primitive, already live on Agents Map's per-agent Communication History panel) — no new CSS.

REQ-SB-02 — Browse & Search (new top-level nav page) — pending browser sign-off

Two new pages, reached from the new vault-browser.html nav item (placement mirroring System Health/Agent Activity's own precedent): list/browse all 496 indexed notes (204 Email, 134 Person, 51 Meeting, 6 Customer, 1 Partner, plus Notifications/Files/ Newsletters — real vault counts from REQ-SB-01-US-01's own direct inspection), filter/navigate by tag, run a ranked keyword/full-text search (not a bare substring match — the example results demonstrate a note ranking above another despite the lower one also containing the literal query text), and — on note-detail.html — navigate a note's forward links and backlinks as a real, clickable list, NOT a visual graph canvas (resolved out of scope this pass, ESC-022). Three independent state-switcher groups on vault-browser.html demonstrate every Gherkin scenario, including the honest "vault not indexed yet" empty state (Scenario 7, distinguished from "indexed, but no matches", Scenarios 5/6). Two small additive CSS primitives (a.item-row/button.item-row, .tag-chip) were added to styles.css so every note row and tag filter is genuinely clickable in a browser, not a decorative mockup — see both files' own top-of-file breadcrumbs for the full design rationale.
