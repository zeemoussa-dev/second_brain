# REQ-SB-95-US-03-T01 — Catalogue Publication Into Agent Context

## Parent Story

- Story: [[REQ-SB-95-US-03]] — `../UserStories/REQ-SB-95-US-03-published-catalogue-and-call-enforcement.md`
- Requirement: `Documentation/PRD.md` → REQ-SB-95 *An Agent Can Only Do What the App Can Do — Operator Profile, Actions, Workflows, Entity Resolution*

---

## Objective

Tell every agent exactly what this app can do, derived from the live catalogue —
a third auto-generated, marker-delimited block in its own SOUL.md, regenerated
by `ActionManager` on every catalogue change, never hand-edited.

---

## Starting State → End State

**Before / Inputs:**

- `app/business/core/agents/agent_manager.py` already owns two auto-generated
  blocks with exactly this idempotent replace-own-block shape (read directly):
  `_SPECIALISTS_BEGIN` / `_SPECIALISTS_END` and `_INDEX_GUIDANCE_BEGIN` /
  `_INDEX_GUIDANCE_END`, each marked "auto-generated by AgentManager -- do not
  hand-edit", each found by `prompt.find(BEGIN)` / `find(END)` and replaced in
  place.
- `SkillManager` calls `publish_section_access_map()` on every deploy/undeploy —
  the derived-republish trigger precedent.
- Nothing publishes anything about Actions.

**After / Outputs:**

- A third marker pair in `AgentManager` and a generator that emits, for ONE
  agent, only the Actions whose `allowed_callers` include that agent's id (or
  are `["*"]`), each with its id, description, inputs with required flags, and
  the one way to call it.
- The block is **removed entirely** when an agent may call nothing — no empty
  shell.
- Regeneration is triggered by the catalogue: `ActionManager.create()` /
  `update()` / `delete()` republish for every affected agent, the way
  `SkillManager` republishes the section-access map.
- Re-running publication is idempotent: the block is replaced between its own
  markers, never appended, and the agent's hand-authored prompt/guardrails/scope
  text around it is byte-identical afterwards.

## Constraints

- Inherits from parent story.
- **Publication is derived, never hand-copied.** No agent's stored prompt text
  may be mutated to carry a hand-written copy of the catalogue.
- `ADR-033`: this is the derived-republish *pattern*, **not** a second JSON
  file. Do not write an `action_catalogue.json` and do not touch
  `section_access.json`.
- **The gate never reads this text** (`REQ-SB-95-US-03-T02` reads the live
  catalogue), so a stale block can mislead an agent but can never let a call
  through. Do not wire the gate to the published block.
- `REQ-SB-33-US-01`'s global honest-uncertainty instruction stays exactly where
  it is — this is not a second instruction beside it.
- Existing agent behaviour is otherwise unchanged: ordinary conversation,
  memory, routing and Skills keep working as they do.

### Why this is `Blocked` — `ESC-072`

Publication writes a real `SOUL.md` through Hermes for every agent whose block
changes, and `allowed_callers: ["*"]` means every agent. The backend suite has no
Hermes sandbox: the four existing Action test files isolate the Action *store* and
nothing else, while the roster they publish to is the live install's.

Measured behind a write-intercepting pytest plugin **before the suite was ever run
with the trigger live**: `test_actions_api.py`, `test_action_resolution.py`,
`test_action_artifact_kind.py` and `test_plugin_actions.py` attempted **123 real
`SOUL.md` writes across all 41 profiles**, 40 `Agent.json` writes, in 5m36s instead
of ~2s. Those blocks would have named real agents after fabricated test Actions and
nothing would ever have removed them.

Fixing it means editing those test files (or adding `tests/conftest.py`) — neither
is in this task's `## Files to Modify`. So the three call sites were left unwired,
with the reason recorded in `publish_action_catalogue()`'s own docstring, and this
task is `Blocked` rather than `Done`.

### Judgement calls inside scope (for human spot-check)

1. **The block names `POST /actions/<action_id>/call`, not the shipped runner
   Skill.** The task requires "the one way to call it"; `ADR-033` fixes the route
   (`T02` builds it) and the runner Skill (`T05` ships it). Naming a Skill that does
   not exist yet would have been a lie, so the block names the route and the caller
   field, and leaves the base URL out — a port in prompt text is instance detail.
2. **No base URL, no confirmation flag, no honest-refusal instruction in the block.**
   Only what the task names (id, description, inputs + required flags, the one way to
   call). `REQ-SB-33-US-01`'s global honest-uncertainty instruction stays where it is;
   the block states the catalogue is complete, which is a fact, not a second guardrail.
3. **"Every affected agent" is computed by offering every agent the regenerated block
   and skipping the ones whose text does not move.** An edit to `allowed_callers`
   affects the agent it was removed from as much as the one it was added to, and
   `["*"]` affects all — a narrower "affected" set would silently miss removals.
4. **A per-agent failure is logged and the pass continues**, and the module-level
   trigger swallows a whole-pass failure. `ADR-033` says the gate reads the live
   catalogue and never this text, so a stale block can mislead one agent but can
   never let a call through — whereas failing the catalogue save over it would lose a
   write the operator already made.
5. **`is_callable_by()` lives on `ActionManager`, not in `AgentManager`.**
   `allowed_callers` is Action data; `T02`'s gate asks the same question of one call
   and can reuse it, so the two cannot drift about what `["*"]` means.
6. **`import_action()` does not trigger publication.** The task names
   create/update/delete only; the import provisioning path is left alone rather than
   widened on my own authority.

### Performance signal for whoever resolves `ESC-072`

The 123 writes took ~2.7s each because publication goes through
`AgentManager.update()`, which does a full registry reload per agent. As specified,
saving one `["*"]` Action in the UI would cost ~110s and rewrite 41 profiles. Worth
deciding alongside the sandbox question.

## Scope extension and operator decision — 2026-10-18 (unblocks `ESC-072`)

**Added to `## Files to Modify`:** `src/backend/tests/conftest.py` (new).

The task shipped `Blocked` because wiring the trigger would have let the existing
Action tests write real `SOUL.md` files — measured at **123 writes across all 41 live
profiles**, plus 40 `Agent.json` writes, taking 5m36s instead of ~2s. There is no
`tests/conftest.py` at all, so nothing sandboxes Hermes for any test in the suite.

Build one: an **autouse fixture, suite-wide**, that points Hermes writes at a temp
`HERMES_HOME` (or otherwise makes a real profile write impossible) so no test can
reach the operator's install. Prove it the way `T02` did — intercept writes and show
that none land outside `tmp_path` and that no Hermes seam is entered — before running
the suite with the trigger live. Do not edit the four existing Action test files; the
fixture is what makes them safe, not changes to them.

**Operator decision on publish cost (2026-10-18): publish in the BACKGROUND, return
immediately.** Saving an Action must not block on republication. Follow the pattern
the vault index rebuild already uses rather than inventing a second one. The operator
accepted the consequence: for a few seconds after a save an agent's `SOUL.md` may
still name the old catalogue, which is acceptable because an agent reads it per
conversation, not per second. If `AC-08`'s wording requires the republish to have
*completed* before the call returns, do not quietly reinterpret it — say so and flag
it, because that is the one place this decision and the locked AC could disagree.

Publication keeps going through `AgentManager` (`ADR-003`'s layering stands); it is the
*waiting* that moves, not the ownership.
