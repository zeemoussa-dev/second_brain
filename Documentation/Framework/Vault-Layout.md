# Vault Layout — where everything lands

The vault is the database, so its folder shape *is* a schema. This page is what
that schema currently is, so a new install can be built to match it and code can
stop guessing.

Templates decide where a note goes; this page records the conventions those
Templates encode. Authoring a Template → **[Templates.md](Templates.md)**.

---

## The root is `Work/`

Not `Notes/`. Every captured thing lands under `Work/<note_name>/`, where
`note_name` comes from the Template.

```
Work/
  Threads/<Subject>/                 one conversation, three note kinds inside
  Notes/<YYYY-MM-DD>/                quick capture, one folder per day
  Files/<YYYY-MM-DD>/<stem>/         one folder per file
  Customers/<Name>/                  durable entity hub
  Partners/<Name>/                   durable entity hub
  Customers/<Name>/Opportunities/<Title>/
  People/                            person notes
  Meetings/                          meeting notes
```

---

## Two folder shapes, and when each applies

**Dated** — `Work/<kind>/<YYYY-MM-DD>-<Title>.md`. For things that happen at a
moment: meetings, notes, captures.

**Name-keyed** — `Work/<kind>/<Name>/<Name>.md`, no date anywhere in the path.
For durable entities you will keep referring to: Customers, Partners,
Opportunities, Threads. In Template terms this is
`note_own_folder` + `note_filename_plain` + a plain folder name.

A name-keyed entity that also carries a running record uses **sibling files, not
repeated filenames**:

```
Work/Customers/<Name>/<Name>.md            the hub note
Work/Customers/<Name>/<Name>-log.md        the running log
Work/Customers/<Name>/<Name>-captures.md   what was captured about it
```

> **Not `index.md` / `log.md` / `captures.md`.** Every file carries the entity's
> own name, so no two folders produce the same bare filename. This matters
> because parts of the system still key on filename stems — see the collision
> rule in `MEMORY.md`.

## Threads — one folder, three note kinds

`Work/Emails/` **no longer exists.** Email capture moved wholesale into the
Threads pipeline, and one thread folder holds three distinct `type` values:

| `type` | What it is |
|---|---|
| `Thread` | One distilled conversation — the thing a list view should show |
| `RawMessage` | One per individual message, with its own `sender` / `subject` / `received` |
| `File` | An attachment |

Code that still checks for a flat `Work/Emails/` folder, or treats an "Emails"
kind folder as meaningful, is reading a dead data source.

**Thread identity is the provider's `conversation_id`**, passed straight through
as the note's `id` — never a minted uuid. A thread therefore has a meaningful
external key from birth and nothing needs backfilling later.

**Threads use `on_existing_title: "always_new"`**, deliberately unlike
Customer/Partner's `"error"`. Two genuinely unrelated conversations sharing a
subject line is normal and correct; two Customers sharing a name is not.

---

## Notes — the quick-capture inbox

`Work/Notes/<YYYY-MM-DD>/<Auto-Generated Title>.md` — one folder per day, one
file per note, **deliberately not filed under any Customer or Partner hub**.

Capture here is fast, lossless and asks nothing. Classification is a separate,
later reasoning pass. Do not add a hub-resolution step to the capture path; that
is what turns a two-second capture into a conversation.

---

## Files — one folder per file, not per day

```
Work/Files/<YYYY-MM-DD>/<filename stem>/<the real file>
Work/Files/<YYYY-MM-DD>/<filename stem>/<filename stem>.md
```

The folder-per-file shape mirrors Thread, Meeting and Opportunity: a folder named
after the thing, holding a same-named `.md` beside the real content. A flat
per-day layout shipped first and was corrected.

> Incoming media can arrive under a cache-mangled name (`doc_<hash>_<real name>`).
> The capture path accepts an explicit filename override for exactly this.

## Child notes — when one note needs a log

An entity that needs a running log and a captures list uses Template `children`
rather than more sections:

```json
"root": {
  "children": ["log", "captures"],
  "children_index_section": "Log & Captures"
}
```

The parent's body then carries `## Summary`, `## Actions`, `## Related` and
`## Log & Captures`, and the engine writes into a child via `modify_section()`'s
`child_suffix` parameter.

> **Availability trap.** Child notes need `create_dynamic_child()`, which exists
> only in the canonical engine at `Hermes-Provisioning/shared/vault_manager.py`.
> The backend's own copy does not have it. See
> [Hermes-Provisioning.md](Hermes-Provisioning.md).

## What lives beside the vault, not in it

The app database folder — `<SECOND_BRAIN_DATA_PATH>`, historically
`<vault>/.second-brain` — holds everything the system needs that is not a note:

```
data/Templates/<id>/Template.json
data/EmailCapture/noise_definition.json
data/Sections/ · data/Tools/ · data/Providers/
pipelines/<id>.json
AGENT-MEMORY.md
```

These are **never repo-tracked files** and never live inside a Skill's `scripts/`
folder. Resolve the folder through `vault_manager.data_root()`, never a hardcoded
`.second-brain` — that hardcoding once cost a full day of silently dropped email
capture.

---

## One thing that is not persisted

The search index is a plain in-process dictionary with **no disk persistence**.
Every backend restart empties Browse & Search back to "nothing indexed yet" until
something calls `rebuild_index()`. Since capture moved out of the backend process,
nothing calls it automatically any more.

If a fresh install looks like it captured nothing, check the index before
suspecting the pipeline.
