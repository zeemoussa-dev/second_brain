### The mechanism

**Second Brain is a framework still being built while it is used.** It is
incomplete and buggy by design at this stage, and much of what follows is the
record of getting somewhere rather than a description of where things are now.
**Reason from the current code, not from this file.** If an entry describes a
subsystem, check it still exists before building on it.

The core mechanism, and the thing to know before anything else:

- **`app/vault/vault_manager.py`** is the one template-driven vault read/write
  engine (`create` / `update` / `modify_section` / `find` / `bump_folder_date`).
- **A new note type is a new `Template.json`, never new code.** The engine's own
  docstring: *"extending what it can write happens by adding a Template.json,
  never by writing a new script."* Templates live at
  `<second_brain_data_path>/data/Templates/<id>/Template.json` and control
  note_name, filename shape, `on_missing`/`on_existing_title`, per-section access
  (`machine_write` vs human-owned, enforced), and frontmatter defaults.
- Frontmatter `id` is the stable identity key — that is what makes a re-run
  idempotent instead of duplicating.

So a capture source (email, calendar, anything) is **a Template plus something
that fetches data**. It is not a subsystem, and it should not need new engine
code.

## Framework reference

Verified against the code 2026-09-04. **This section exists so a session does not
have to grep the engine to learn what it can do.** The full authoring guides live
in `Documentation/Framework/` — this is the condensed reference. If you find yourself reading
`vault_manager.py` to answer "what keys does a Template take" or "what can the
engine do", that is a bug in this section — fix it here.

### The vault engine — `src/backend/app/vault/vault_manager.py`

| Call | What it does |
|---|---|
| `create(vault_path, template, note_name, title, note_id=None, frontmatter=None, sections=None, folder_date=None)` | New note. `folder_date` overrides the folder's dated stem (only with `note_own_folder`). |
| `modify_section(vault_path, template, note_id, section, content, mode, note_name=None, title=None, frontmatter=None)` | **"Create if not exist, else update section" in ONE call.** `mode`: `"replace"` or `"append"`. Omit `note_name`/`title` to force "must already exist". |
| `update(vault_path, note_path, title=None, frontmatter=None)` | Rename/retitle in place — nothing moves, no backlink breaks. |
| `find(vault_path, by, value, note_name=None)` | `by`: `id` \| `filename` \| `folder`. Also `find_by_id`, `find_by_filename`, `find_in_folder`. |
| `bump_folder_date(vault_path, note_path, new_date_str)` | Move a container note's folder sort-date forward. |
| `load_template(vault_path, template_id)`, `read_note`, `write_note`, `get_section_content` | Primitives. |

**Paths.** Notes root is **`Work/`** (`_NOTES_ROOT`), not `Notes/`. A note lands at
`Work/<note_name>/<YYYY-MM-DD>-<Title>.md`, or with `note_own_folder: true` at
`Work/<note_name>/<YYYY-MM-DD>-<Title>/<YYYY-MM-DD>-<Title>.md` so attachments can
sit beside it. Templates resolve to `<second_brain_data_path>/data/Templates/<id>/Template.json`
in the backend copy, and `<vault>/.second-brain/data/Templates/...` in the Hermes-Skill copies.

**Identity.** Frontmatter `id` is the stable key — caller-supplied external id, or
uuid4. The engine also stamps `title` and `created`. Keying on a real external id
is what makes a re-run idempotent instead of duplicating.

### `Template.json` — the ONLY keys the engine reads

| Key | Meaning |
|---|---|
| `id` | template id (= its folder name) |
| `note_name` | subfolder under `Work/` |
| `on_missing` | `create` (default) or `error` — `error` means never silently create |
| `on_existing_title` | `update_section` (default) = same title updates in place; otherwise always a new file |
| `note_own_folder` | bool — give each note its own folder |
| `note_filename_plain` | bool — drop the date prefix from the filename |
| `sections` | `[{ "name": str, "access": str }]` |
| `frontmatter_defaults` | dict merged into every note's frontmatter |

**Section access vocabulary: `machine_write` \| `human_only` \| `public`.** An
**undeclared** section defaults to `machine_write` (open), so a section you want
protected must be declared. `human_only` is enforced by the engine —
`_require_machine_write` raises, so it is structural, not a prompt instruction.
Vault convention: `## Actions` and `## Personal Notes` are the human-owned ones.

**A new note type is a new `Template.json`, never new code.**

### Artifacts — what moves between installs

Four kinds: **skill**, **template**, **agent**, **pipeline**. Three archive
formats, easily confused:

| Format | Carries | Modules |
|---|---|---|
| `.sbf` | the four artifact kinds (`ADR-013`) | `artifact_export.py`, `artifact_import.py`, `sbf_archive.py` |
| `.sbb` | Hermes structural backup — profiles, cron, skills | `tools/hermes_backup.py`, `hermes_restore.py` |
| `.sbd` | real vault **data** export | `sbd_archive.py` |

Supporting: `artifact_dependency_resolver.py` (export closure),
`artifact_secret_scan.py`, `artifact_import_conflicts.py` (import gates on an
explicit per-artifact decision when `conflicts: true`, never defaults silently),
`artifacts_inventory.py`. Placeholder substitution keeps machine-specific
absolute paths out of travelling content — but **cannot catch a hardcoded
RELATIVE path**, and a restore recreates **no `.env` anywhere**.

- **Email/threaded-source template shape (`email-thread`, 2026-09-04):** a threaded source is ONE note per thread, not one per message, keyed on the provider's own conversation id as frontmatter `id`. `modify_section(note_id=<conversation id>, section="Messages", mode="append")` is "create if not exist, else append" in a single call, so a re-run of the same message set appends to the same file instead of duplicating -- verified live (2nd call on the same id returned `created: False, updated: True` on the same path). `note_own_folder: true` gives the thread its own folder so attachments sit beside the note. Sections split by real ownership using the vault's established access vocabulary (`machine_write` / `human_only` / `public`): `Summary` + `Messages` machine-written, `Actions` + `Personal Notes` `human_only` -- the engine REFUSES an automated write to those (`_require_machine_write` raises), so human ownership is structural, not a prompt instruction anyone can drift from. Confirmed live. The same shape fits any threaded source (chat, tickets), not just email.

- **Embedded-attachment dual-syntax resolver shape (`ADR-016`, `REQ-SB-86-US-02-T01`):** given a plain `list[str]` of vault-relative `.md` paths (no runtime dependency on however the selection was built), read each note's real body via `app/obsidian/frontmatter.py::read_note`, scan it with two separate regexes (a wikilink-embed `!\[\[([^\]|#]+)(?:[#|][^\]]*)?\]\]` and a markdown-image-link `!\[[^\]]*\]\(([^)\s]+)\)`), and resolve each captured target in a fixed fallback order: (1) relative to the referencing note's own containing folder — the real, dominant convention this vault's own notes actually use; (2) every ancestor folder from the note's own folder up to the vault root, recursively searched for the target's own bare filename under an `attachments/`/`files/` subfolder (the real `write_attachments()`/`write_file_companion()` convention) — searching by filename rather than replicating the exact note-slug/message-slug nesting keeps this resolver decoupled from that convention's own internal shape; (3) as a plain vault-root-relative path. A target resolving nowhere is silently skipped, never fabricated, never a hard failure. **Always call `.resolve()` on both the matched path and the vault root before computing the final vault-relative string** — a match reached via a `../` relative traversal from the note's own folder (e.g. a markdown-image-link target) produces a non-normalized path that otherwise fails to dedup against the SAME physical file reached directly by a sibling note; found live via a real two-note dedup check, not by inspection. A target that itself resolves to a real `.md` file is excluded (Obsidian's `![[Note]]` embed syntax is transclusion, not an attachment — including it would silently expand an export beyond the operator's own selection). First concrete instance: `vault_attachment_resolver.py::resolve_embedded_attachments`. Apply the same shape to any future "detect a real on-disk reference inside a note's own body" resolver.

- **Genuinely-unfiltered filesystem-tree read shape (`REQ-SB-86-US-01-T01`):** a real, uncached recursive walk built directly on `Path.iterdir()`/`Path.relative_to()` over `settings.vault_path` (never `vault_writer.list_all_note_paths()`/the in-memory note index, which deliberately excludes OKF-reserved files and `_`-prefixed folders) — sort folders-before-files by computing `child.is_dir()` ONCE per entry and reusing that single boolean for both the sort key and the type decision (see the Constraint below for why calling `is_file()`/`is_dir()` independently is unsafe). First concrete instance: `VaultManager.get_export_tree()` / `GET /vault/export-data/tree`. Verified live: a 4081-entry independent `Path.rglob("*")` cross-check against the real vault matched the endpoint's own flattened output byte-for-byte (0 missing, 0 extra).

- **Message-note readable filenames need time-of-day, not just date, or they collapse right back into indistinguishable names.** `<date> <sender>` alone (the first fix for "messages in a thread all have the same title") still fails whenever the SAME sender posts more than once in a thread on the same day — the common back-and-forth case — since the hash-suffix collision fallback produces a second filename that still just *reads* as "Name" in Obsidian's file view. `<date> <HH:MM> <sender>` fixes it directly and is more informative than a hash. Found live 2026-08-21 during the first real vault-rebuild pull; fixed in both `vault_lib.py` (Hermes-native Skill) and `app/data_access/vault_writer.py`'s `raw_message_note_path`.

- **Raw-HTTP direct-to-LLM client shape (`ADR-011`):** a new `app/data_access/<provider>_client.py` — raw I/O only (build request, send via `httpx`, parse response), a dedicated `<Provider>ClientError(Exception)` raised on every real failure path (network error, timeout, non-2xx, or a response body that doesn't parse into the expected shape — wrap parsing in `try/except`, never let a `KeyError`/`IndexError`/JSON-decode failure escape unhandled), consumes `app.config.settings` directly at call time rather than through the entity's own CRUD Manager (a Manager owns config-at-rest, not runtime dispatch). Mirrors `app/hermes/rest.py`'s existing `httpx`-direct pattern one layer over; first concrete instance is `compass_client.py` (`REQ-SB-82-US-06-T02`). Apply the same shape to any future direct-to-LLM-provider client.

- **Client-side-only "reply to this message" context anchoring, when no backend persistence exists for a chat surface (`ADR-012` point 5):** assign a purely in-memory, never-persisted `localId` to each message at append time (a simple incrementing counter is enough — no `crypto.randomUUID()` needed); on send, resolve the selected `localId` against the CURRENT in-memory message array (a stale/unresolvable reference just falls through to a plain, unanchored send — never a crash or a blocked Send) and prepend the referenced message's own text as a quoted prefix (`"> {parentText}\n\n{newText}"`) to the text actually sent to the backend — never to the rendered bubble, which always shows only the user's own typed text. Clear the selection on every existing thread-reset path (new-chat/agent-switch), not just after a successful send. Built for `AgentChatPanel.tsx` (`REQ-SB-82-US-06-T08`); reusable for any other single-recipient chat surface that wants a reply-to hint without a real message-id/persistence layer.

- **LLM-composing routing/decision function shape (`ADR-012` point 2):** a business-layer function that reasons over real, given data (a roster/history/message, never a hardcoded scenario) should (1) compose the relevant `data_access/<provider>_client.py` module (never `httpx` directly, never a business-layer import from another business module), (2) build the prompt in a dedicated private helper that takes the real given inputs as plain parameters (never reaches into a store/global itself — keeps the function pure/testable via monkeypatch), (3) parse the model's raw reply with a STRICT match against only the real, given candidate set (e.g. a word-boundary-scoped regex over exactly the ids handed in) — returning `None` on zero or 2+ matches, never fabricating/coercing to the nearest string, and (4) deliberately does NOT catch the client's own dedicated error type — the degrade decision belongs to the caller, one layer up, not the routing function itself (mirrors `_reply_via_agent`'s own established try/except-degrade shape, applied one level higher, at the routing decision rather than the reply-generation step). First concrete instance: `moderator.py::route_question_llm` (`REQ-SB-82-US-06-T03`). Apply the same shape to any future LLM-composing routing/decision function.

- **A frontend API client function that needs the raw `Response` (e.g. `.blob()` for a real file download) bypasses the shared `api/client.ts::apiFetch` helper entirely — that helper always resolves via `response.json()`, so it cannot serve a binary/file response.** The bypassing function issues its own `fetch()` call, re-reads `VITE_API_BASE_URL` locally (duplicated, since `client.ts`'s own `BASE_URL` constant isn't exported) and re-implements the same non-2xx → `ApiError(status, await response.text())` mapping `apiFetch` uses, so callers still get one consistent error shape regardless of which path served the response. First concrete instance: `artifactsApiClient.ts::commitExport` (`REQ-SB-85-US-02-T05`), which returns the real downloaded `.sbf` bytes. Apply the same shape to any future endpoint whose real response is a file, not JSON.

- **Narrowly-scoped import-only write path for an otherwise read-only Manager (`ADR-015`):** `data_access/<entity>.py` gains a raw `write_<entity>_json(id, data)` (zero validation, zero defaults, creates its own target directory if missing, always overwrites); the Manager gains a matching `import_<entity>(id, data) -> Entity` that (1) validates `data` by round-tripping it through the Manager's own EXISTING read-side parser (e.g. `_to_pipeline`/`_to_template`) first — a malformed shape raises there and nothing is ever written to disk — then (2) calls the new data_access writer, then (3) returns `self.get_by_id(id)` (read-your-own-write). The Manager's own module docstring is updated in the same change so a stale "read-only for now" claim never sits next to a real writer. First concrete instance: `PipelineManager.import_pipeline` (`REQ-SB-85-US-03-T04`); same-shape sibling `TemplateManager.import_template` (`REQ-SB-85-US-03-T03`). Apply the same shape to any future Manager that needs a narrowly-scoped write path added for one specific caller (e.g. import provisioning) without becoming a general authoring UI.

- **Frontend two-phase upload → preview → per-item-decision → commit flow shape:** keep the real, user-selected `File` object in component state (never just its parsed preview response) and re-submit the SAME `File` at commit time, since a two-phase backend (`ADR-013`'s own "preview never writes, commit re-parses fresh") never trusts a cached preview either. A per-conflicting-item 3-way decision control renders independently per item (never one shared control for a whole batch), keyed the SAME way the backend's own decisions map expects (`f"{kind}:{id}"` here) so the client-side key and the outgoing `Form`/JSON field never have to be re-derived differently. The commit action stays genuinely `disabled` (not just visually deprioritized) until every conflicting item has one of its real choices selected. First concrete instance: `SettingsArtifactsPage.tsx`'s Import flow (`REQ-SB-85-US-03-T06`), sibling to the same page's own Export dependency-preview/secret-scan-confirmation flow (`REQ-SB-85-US-02-T05`) which already established the two-phase shape one step earlier. Apply the same shape to any future upload-then-resolve-conflicts UI.

- **`.sbd` real-vault-data-export orchestrator shape (`ADR-016`, `REQ-SB-86-US-02-T02`):** a thin `business/logic/` orchestrator (`vault_export.py::build_export`) composes an already-built resolver (`T01`'s `resolve_embedded_attachments`) with a pure zip writer (`sbd_archive.py::write_archive(output_path, members: dict[str, str])`) — the writer takes ONLY a flat `{archive_member_path: source_file_path}` mapping and makes zero business decisions (no manifest, unlike `sbf_archive.py`'s always-writes-`manifest.json` shape); every decision (which files belong, hierarchy-vs-flat member-path computation, flat-collision disambiguation) happens in the orchestrator, one layer up. Flat-collision disambiguation groups the whole export set (selection + resolved attachments) by basename FIRST, then renames every entry in any group with count > 1 by prefixing `Path(relative_path).parent.name` (real, on-disk casing, no forced-lowercase) — falls back to the literal string `"root"` when the colliding file sits directly at the vault root (empty parent name). The router route mirrors `REQ-SB-85-US-02-T04`'s own `/commit` shape exactly: build to a scratch temp path, `background_tasks.add_task(os.remove, scratch_path)`, stream via `FileResponse` with an ISO-8601-UTC-timestamped filename. First concrete instance: `POST /vault/export-data/export`. Apply the same shape to any future "compose a resolved file set into one real, member-path-computed archive" export.

- **Frontend folder-tree multi-select shape — selection `Set<string>` holds only FILE paths, never a folder's own path (`REQ-SB-86-US-01-T02`):** a folder checkbox's checked/indeterminate-equivalent state is DERIVED at render time (every real file path nested beneath it, computed by a pure recursive walk over the already-fetched tree, is present in the selection `Set`) rather than the folder itself ever being written into the `Set` as its own entry. Toggling a folder checkbox adds/removes every one of its descendant file paths at once (add if not-all-selected, remove if all-already-selected); an individual file checkbox toggles just its own path, independent of any folder. This keeps the exposed selection state a flat, ready-to-consume file list for a downstream export trigger (no folder-vs-file disambiguation or re-expansion needed by the consumer). A separate client-side-only quick-filter (e.g. `.md`-only) narrows what's RENDERED (drop a file that fails the predicate; drop a folder once every one of its children was dropped) via a pure function over the same already-fetched tree — it must never read or write the selection `Set`/expand-state, so toggling it on/off is always non-destructive to both. First concrete instance: `SettingsVaultExportDataPage.tsx`. Apply the same shape to any future folder-tree-style multi-select UI in this app.

- **`.sbd` frontend export-trigger shape — expansion already happened upstream, don't redo it (`REQ-SB-86-US-02-T03`):** when a downstream frontend task's own spec describes "expand a folder selection into real file paths before sending the request," always re-read the REAL current upstream page's own selection-state design first — if that upstream task's own `Set<string>` already holds only file paths (expanded at select-time, not confirm-time; see the `REQ-SB-86-US-01-T02` Pattern above), the downstream task's own "expand on confirm" step is already satisfied by construction and needs zero new expansion code, just `Array.from(selection)` passed straight through. Log this as a scope-internal reconciliation, not a re-spec. First concrete instance: `SettingsVaultExportDataPage.tsx`'s export-options flow. Apply the same check to any future "confirm step consumes an already-built upstream selection" UI.

- **Structurally strip a cloned Hermes profile down to a bounded, zero-tool relay target — don't rely on SOUL.md prose alone (`REQ-SB-87-US-03-T02`):** `hermes profile create <name> --clone` inherits the source profile's FULL skill set and `platform_toolsets.cli` list — for a profile meant to be reached only via one-shot `chat -q` with everything it needs already embedded in the question text (no tool use required or wanted), delete the cloned profile's entire `skills/` directory (`hermes skills opt-out --remove --yes` alone only strips *bundled* skills, not *local*/project-specific ones also copied by `--clone` — those need direct filesystem removal) AND edit the profile's own `config.yaml` → `platform_toolsets.cli: []`. This makes "no vault-write capability, no tool-calling loop" a real, structural property (confirmed live via `sessions export`'s own `tool_call_count: 0`), not just something the prompt asks for. Apply to any future bounded, non-agentic relay-target profile.

- **Real Hermes cron provisioning (`REQ-SB-88-US-01-T04`) — a new job's `--skill` only resolves against the PRIMARY/default profile's own enabled skill catalog, not the specialized per-Skill profile the script actually lives under.** `hermes cron` jobs are stored in one central `cron/jobs.json` with no per-job profile field; they fire from whichever Hermes profile's own gateway is the "running" one (`hermes profile list`'s `◆` marker) — confirmed live: the already-working `job4-summarize-tag-threads` job's own `summarize-and-tag-threads` skill is enabled on the `default` profile (`AppData/Local/hermes/skills/`), NOT on any specialized profile. A brand-new Skill only ever deployed to its own dedicated profile (e.g. `summarize-and-tag-files` under `files-manager`, whose gateway shows `stopped`) must ALSO be enabled on the primary/default profile (move it out of that profile's own `_disabled-skills-on-primary/<group>/<skill>/` staging folder into `skills/<group>/<skill>/`, then deploy the migrated scripts there too) before a new cron job naming it via `--skill` can actually run. Apply this check before provisioning any future first-time cron job for a Skill that currently lives only under a specialized profile.
- **`hermes cron create SCHEDULE ...` schedule-string syntax is a real, silent trap: a bare duration (`"20m"`) creates a ONE-TIME job (`schedule.kind: "once"`, fires once then is done regardless of `--repeat`); only the `"every "`-prefixed form (`"every 20m"`) creates the real, recurring `schedule.kind: "interval"` job.** Found live, `REQ-SB-88-US-01-T04` — a first attempt with `"20m"` alone silently produced a one-shot job (caught by reading the created job's own JSON entry before triggering it, not assumed from the CLI's own success output, which looks identical either way: `"Schedule: once in 20m"` vs `"Schedule: every 20m"` — read the `Schedule:` line in the CLI's own confirmation output, or the raw `cron/jobs.json` entry, before trusting any newly-created recurring job actually IS recurring).

## Constraints

- **Settled vocabulary, do not drift: `Tool -> Skills -> Actions`. A TOOL is a group of SKILLS managing a set of ACTIONS** (operator, 2026-09-04). Three different things in this codebase have been called "tool", which is why every discussion of it drifted: (1) **Tool** as defined here -- the Skill grouping, `<data>/data/Tools/<tool>/Skills/<skill>/`, live and load-bearing (`SkillManager` resolves Skill metadata through it); (2) **the Hermes toolset** -- Hermes' own built-in capabilities (`terminal`, `file`, `memory`, `browser`), a different vocabulary owned by a different system, which is what `GET /tools` and an Agent's `tools` field actually mean; (3) a dead `Tool -> Category -> Action` MCP mounting layer (`data_access/system/tools/`), an abandoned trial, REMOVED 2026-09-04 (it had still been wired into `main.py`, registering nothing, long after a 2026-08-27 entry described the backend's own MCP tool server as already retired -- the retirement was partial and the mounting code outlived it). The TAXONOMY of (3) was right and survives as (1) -- MCP as the *delivery mechanism* is what failed, and Skills became Hermes-native scripts instead (`ADR-002`). That is exactly why the dead code reads as though it were the live model. Always write "the Hermes toolset" for (2), never "Tools". Full framing: `Documentation/Framework/README.md`.
- **`src/backend/app/vault/vault_manager.py` is an OLDER engine than the memory around it describes: it has NO `create_dynamic_child()` and NO per-caller section access.** Those (`ADR-017`, `REQ-SB-87-US-01-T01/T02`) live only in the canonical `Hermes-Provisioning/shared/vault_manager.py`, which is held outside the working tree by default and brought back when needed. The backend copy reads exactly six Template keys -- `sections`, `on_missing`, `on_existing_title`, `note_own_folder`, `note_filename_plain`, `frontmatter_defaults` -- and its access check is a flat `sections[].access`, where an UNDECLARED section defaults to `machine_write` (open), so a section you want protected must be declared explicitly. Practical consequence: a "container note with one child note per item" shape is NOT available in the current code; use one note plus an appended section instead. Also note this copy deliberately drops the `.second-brain` prefix when resolving Templates (it is passed `second_brain_data_path` directly, not `vault_path`) -- a comment in the file says to RE-APPLY that line if the engine is ever re-copied from a canonical source.

- **This corporate network re-signs all outbound HTTPS through a G42 middlebox (`*.<host>` → `G42Decrypt (t)` → `G42Decrypt` → `AD-EC-CA-01-CA`, sha1 `1BE89EE7E18FDB1264739C0AC1C221F93C030F18`), and Node ignores the Windows trust store — so ANY Node-based integration fails TLS on this machine until `NODE_OPTIONS=--use-system-ca` is set (Node ≥ 22.15).** Solved live 2026-08-20 while linking Hermes to WhatsApp. The cost of not knowing this is high because **every layer reports a different, plausible, wrong cause**: Baileys wraps the WebSocket error in a Boom with a generic `statusCode: 500`, which collides with `DisconnectReason.badSession` (500); `bridge.js` hardcodes `pino({ level: 'warn' })` and therefore discards the real `UNABLE_TO_GET_ISSUER_CERT_LOCALLY` before it can print; the gateway then reports only "WhatsApp enabled but not paired". Four hours went into chasing corrupt sessions, rate limiting, and stale processes — none of which existed. **Whenever a Node-based integration on this host fails in a way that mentions a session, a handshake, a 500, or a bare "connection closed", check the TLS chain FIRST** (`node -e` + `tls.connect({rejectUnauthorized:false})` and walk `getPeerCertificate(true)`) before believing any error message the library produces. The same class of problem is already solved for Python by `pip_system_certs` in the Hermes venv — that package's presence on a machine is itself a signal that interception is active. Never "fix" it with `NODE_TLS_REJECT_UNAUTHORIZED=0` (disables verification outright); prefer `--use-system-ca` over a `NODE_EXTRA_CA_CERTS` PEM snapshot, since the latter breaks silently on CA rotation. Full runbook in `Deployment.md` §1.

- **Verifying a fix from a shell whose network egress differs from the user's own shell produces confident, wrong conclusions.** Found live 2026-08-20: the WhatsApp bridge was run four times from Claude Code's tool shell (which is not behind the G42 interception) and produced a valid QR in ~1.2s every time, while the identical command in the user's interactive PowerShell failed on every attempt. That asymmetry was read as "the bridge is fine, something about your invocation is wrong", and an entire rate-limiting theory was built on top of it — including a pointless cooldown — before the real error surfaced. **When a command succeeds in the agent's shell but fails in the user's on the same machine, treat the environment difference itself as the primary hypothesis, not a curiosity** — and prefer having the user run the diagnostic in their own shell over re-running it locally and reporting success.

- **A `Pipeline`'s own `PipelineStep.id` (e.g. "fetch-meetings") carries NO real Agent/Skill linkage — it exists purely to drive the Job Tree visualization. The ONE real path from a Pipeline to the Skill that implements it is `cron_job_id`/`cron_profile_id` → the live Hermes cron job (`HermesCron.list_cron_jobs`/`get_cron_job`) → that job's own `skill` field.** Found live 2026-09-01 (`BUG-041`): `artifact_dependency_resolver.py`'s Pipeline branch had been trying to resolve each step id as an Agent id, which silently failed 100% of the time (steps are never real Agent ids) — no Pipeline export ever included its real Skill until fixed. The cron job's own `skill` field is inconsistent in shape across real jobs — confirmed live: bare slug for some (`meeting-capture-recurring` → `"meeting-capture"`), Hermes' raw `"<category>/<slug>"` form for others (`azure-kb-refresh` → `"knowledge-base/azure-kb-writer"`), and empty for real jobs that aren't Skill-backed at all (git-sync, index rebuilds) — always normalize via the last `/`-segment and treat empty/missing as "no Skill", the same convention `Agent.skill_ids` already established. `PipelineManager.get_implementing_skill_id()` is the composed helper; use it rather than re-deriving this lookup elsewhere.

- **A `<a download>` + `URL.createObjectURL` blob download (this app's own established client-triggered-download technique, `REQ-SB-85-US-02-T05`/`REQ-SB-86-US-02-T03`) can show `receivedBytes` reaching `totalBytes` in full on `Browser.downloadProgress`, then transition straight to a terminal `canceled` state with no file landing on disk — reproduced identically on BOTH flows in a real headless-Edge + CDP `Browser.setDownloadBehavior` session.** A same-session control check (re-running an already-`Done` sibling flow's identical, unmodified code) is what correctly isolated this as a CDP-headless/`blob:`-URL-download-interception environment/tooling quirk, not a defect in either flow's own code — a speculative fix (delaying `URL.revokeObjectURL`) made no observable difference and was reverted. Before concluding a "browser download fires" AC has failed in a CDP-headless verification session, reproduce the same symptom against an already-shipped sibling flow using the identical download technique; if it reproduces identically, treat the request-shape + response-byte-integrity + `downloadWillBegin`-with-full-byte-transfer evidence as sufficient proof, and disclose the terminal-state quirk rather than blocking the task or silently claiming an unverified full pass. `Page.setDownloadBehavior` (the older CDP domain) produced zero download-interception events at all on this project's current Edge build (`Edg/151.0.4129.107`) — `Browser.setDownloadBehavior` is the domain that actually works.

- **`CORSMiddleware` response headers are not attached to a FastAPI/Starlette response built from an UNHANDLED exception — a route that raises a raw Python exception returns a real, readable status/body to a direct call (`curl`), but the SAME request from a browser is opaque-`CORS`-blocked (`TypeError: Failed to fetch`, no readable status), found live 2026-09-01 against `POST /vault/export-data/export` with a genuinely non-existent selected path.** A route's own already-handled error branches (e.g. Pydantic validation → `422`) are unaffected — those responses build within the normal middleware stack and DO carry CORS headers correctly, confirmed directly. Before assuming a browser-observed "Failed to fetch" on a real backend route means the request never reached the server, check whether the SAME request succeeds via a direct `curl`/non-browser call — a real, readable non-2xx response there with an opaque browser-side failure is this exact CORS-on-unhandled-exception gap, not a network/CORS-config issue with the route's own normal-path headers.

- **This vault's real, current OKF Customer/Partner directory convention does NOT literally repeat `index.md`/`log.md`/`captures.md` filenames across folders as `REQ-SB-54`'s original naming implied — the real, live convention (confirmed 2026-09-01 while verifying `REQ-SB-86-US-02-T02`) is `<Name>.md`/`<Name>-log.md`/`<Name>-captures.md`, each already disambiguated by the entity's own name.** A flat-extraction filename collision therefore does NOT occur naturally between two different real Customer/Partner folders today — it can still occur between any two files that happen to share a bare filename for other reasons (e.g. two attachments both named `diagram.svg` in different folders), so the collision-disambiguation logic itself is still required and correct, just not exercised by the specific "two Customers' own `index.md`" scenario the story's own illustrative text assumed. Worth checking directly against real content before assuming a specific "natural" collision case exists, rather than trusting an older story's own naming description.

- **On this Windows host, `Path.is_file()`/`Path.is_dir()`/`Path.exists()` all silently return `False` for a real, existing path once its full string length exceeds ~260 chars (the legacy `MAX_PATH` limit) — and calling `is_file()` and `is_dir()` independently on the SAME long path can therefore silently disagree with whatever branch logic already decided its type, even though both individually just return `False`/`False` rather than raising.** Found live 2026-09-01, `REQ-SB-86-US-01-T01`: 20 real `.md` files in the real vault (all inside an already-archived `Work/_archive/...` tree, paths 261–304 chars) triggered this — `iterdir()` still lists them correctly, but a naive `sorted(..., key=lambda p: (p.is_file(), ...))` sort key disagreed with a separate `if child.is_dir(): ... else: file` branch decision, desyncing display order from actual classification. Fix: compute `is_dir()` (or `is_file()`) exactly ONCE per path and reuse that single boolean everywhere a type decision is needed for that path — never call the predicate a second time expecting the same answer. Before trusting any `Path.is_file()`/`is_dir()`/`exists()` call as a source of truth over a filesystem walk whose entries could plausibly exceed ~260 characters, verify directly rather than assuming.

- **A retrofit/backfill driver for the `email-thread-capture` pipeline that calls `ingest_email.py` DIRECTLY (one message at a time, to prove ingest/dedup/classification correctness in isolation) does NOT get `rename_thread.py`/`link_person_to_thread.py` for free — those only run automatically as part of `run_full_capture.py`/`run_delta_capture.py`'s own per-email loop (steps "2b"/"2c"), which a direct-`ingest_email.py` driver bypasses entirely.** Found live 2026-09-02, post-hoc against `REQ-SB-87-US-02-T05`'s already-`Done` real 100-message retrofit: 4 of its 5 genuinely-new real Threads (plus one older, pre-migration Thread from before this session) were left stuck on their raw `conversation_id` directory name — not a `rename_thread.py` defect (confirmed: invoking it directly against the real vault renamed all 5 correctly on the first try) but a real gap in the retrofit driver's own scope. Corollary: the 16 `SKILL.md` implementations under `Hermes-Provisioning/skills/` exist ONLY there — the Registry stores `skill_ids` but no Skill bodies — so that folder is not obsolete despite its stale cron declaration and "Applied" log.

- **Second Brain's `COMPASS_BASE_URL` is the FULL chat-completions URL; Hermes' own Compass `base_url` must NOT end in `/chat/completions`. The two conventions are opposites and both are correct for their own consumer.** `data_access/compass_client.py` POSTs to `settings.compass_base_url` verbatim and appends nothing, so a bare host 404s at first real use; Hermes appends the suffix itself, so including it there produces the base_url double-append bug `Hermes-Provisioning/config/custom_providers.yaml` already documents. The setup wizard checks for the suffix and says so in its own field help, because this is otherwise only discovered hours after setup.

- **Never write a bare `KEY=` into `.env` for a Path setting.** pydantic parses an empty string into `Path(".")`, not `None` -- an empty `SECOND_BRAIN_DATA_PATH` silently relocates the app's whole state folder to whatever directory the backend was started from, AND suppresses `config.py`'s own validator that would otherwise default it to `<vault>/.second-brain` (the field is no longer None, so the default never applies). `system_settings._write_env_updates` removes a key's line instead of blanking it. Verified live 2026-09-04.

- **The first Compass request over a cold connection is reliably reset by the corporate TLS middlebox (`[WinError 10054]`); the immediate retry succeeds.** Verified live 2026-09-04: attempt 1 reset, attempts 2 and 3 both HTTP 200 with identical credentials. Anything that reports Compass reachability to a human must retry once on a CONNECT-level failure or it will report a false failure for correct settings. Never retry an HTTP-level failure (400/401/404) -- those are real answers from the server. Note `data_access/compass_client.py` itself still has no such retry, so genuine app-side Compass calls remain exposed to this (plausibly related to the still-open `BUG-015`).

- **Every Hermes-side Skill script must resolve the App Database Folder through `vault_manager.data_root()`, never a hardcoded `<vault>/.second-brain`.** `data_root()` honours `SECOND_BRAIN_DATA_PATH` and falls back to the historical in-vault location. Hardcoding it caused the 2026-09-04 outage: the 2026-09-03 config/vault split moved templates out of the vault, `load_template()` then raised for EVERY email, `run_delta_capture.py` swallowed the non-zero exit, and the watermark advanced anyway -- 54 real emails consumed, none written, none recoverable without a manual watermark rewind. The same bug had silently emptied the person ignore list. `Hermes-Provisioning/shared/vault_manager.py` is canonical; fix there, then re-copy to all 12 skill copies.

- **A capture watermark may never advance past an item that failed to write.** Advancing past a failure converts a transient error into permanent data loss, because the next run treats those items as already captured. Re-ingesting an already-written email is idempotent (keyed on conversation/message id); skipping one is not recoverable. `run_delta_capture.next_watermark()` stops just below the oldest failure and is unit-tested. Corollary: never write `if code == 0:` with no `else` around a subprocess whose failure means data was dropped -- that single missing branch is what hid the outage for a day.

- **The Artifacts export/import placeholder mechanism cannot catch a hardcoded RELATIVE path.** It substitutes absolute paths (`@@SECOND_BRAIN_DATA_PATH@@` etc.); a literal like `.second-brain` baked into a script's source passes through untouched, so importing a pre-fix bundle silently overwrites a corrected script. `business/logic/artifact_import_compat.py` screens incoming bundles for this at PREVIEW time (the last point the operator can still skip the artifact) and flags it in the import modal. Detection rule: the script mentions the legacy folder name AND does not route through `data_root`.

- **Hermes gives every profile its OWN home, and env files do NOT chain.** `hermes_constants` sets `HERMES_HOME` to `<root>/profiles/<name>` in profile mode, and `env_loader.load_hermes_dotenv` loads exactly `<that home>/.env` -- there is no fallback to the top-level file. So a value must exist in all 41 places (home + 40 profiles) to be visible everywhere; that is also why `hermes profile create --clone` copies `.env`. Verified 2026-09-04, after asking whether the 41 copies were redundant: they are redundant DATA (all 40 profile files were byte-identical) but structurally required. The wizard writes all of them and its Hermes step now reports drift, because nothing in Hermes notices when one falls behind.

- **Backup carries no `.env` and restore never recreates one.** `hermes_backup.py::_is_excluded` skips any `.env`/`.env.*` file anywhere as a secret. A restored install therefore has every profile, Skill and cron job but zero environment variables -- nothing resolves until the setup wizard is re-run to rewrite them. Provider credentials beyond Compass still need re-entering by hand.
